# Security — Designer Kid

A basic security review of the Designer Kid code, SQL and deployment configuration, carried out by reading the repository and
running `npm audit` (no exploitation or live testing was attempted). The architecture is a static React SPA on GitHub Pages
talking directly to Supabase with the publishable key, so **Row Level Security (RLS) and `security definer` functions are the
only authorisation layer**. The design is sound for a small, admin-authored learning site: no secrets are in the repo, the
admin role is isolated, and anonymous visitors can only read published content and write analytics events (and, once migration
003 runs, reviews). The main risks are abuse of the anonymous write paths (no rate limiting or captcha), drift between the SQL
in the repo and the live database, Supabase Auth settings that cannot be verified from code (sign-ups, password policy), and the
usual XSS-to-session-theft exposure of a browser-stored admin session with no Content Security Policy.

Last verified: 30 Sep 2026 (docs v2.0)

**Status legend.** **Confirmed** = seen in code/config or verified at hand-off · **Inferred** = reasoned from code (reason given) ·
**Unknown** = not verifiable from the repository (what to check is stated). Severity is relative to this project (public
learning site, one admin, no payments, no learner accounts): **High** / **Medium** / **Low** / **Info**.

## 1. Findings

| # | Risk | Severity | Location | Explanation | Suggested fix |
|---|---|---|---|---|---|
| 1 | Anonymous inserts into `events` (spam, analytics poisoning, `user_name` spoofing) | **Medium** | `supabase/schema.sql` lines 104–106; `src/data/supabaseStore.ts` line 160 | Policy `events: anyone inserts own` allows the `anon` role to insert any number of rows with `user_id` null, any allowed `type` (including fake `signup`, `booking_clicked`), any `detail` ≤ 300 chars and any `user_name` ≤ 120 chars (e.g. "Admin"). Only `content_published` is blocked. Anyone with the public key can flood the admin activity feed and grow the database (500 MB free-plan limit). Confirmed. | Restrict anon inserts to the event types the site really emits anonymously (`level_selected`, `lesson_completed`, `challenge_submitted`, `booking_clicked`); force `user_name` server-side (trigger: `'Guest'` when `auth.uid()` is null); add a scheduled cleanup/retention; consider routing events through an Edge Function with rate limiting, or drop anonymous event logging. |
| 2 | Anonymous review submissions after migration 003 (spam / impersonation) | **Medium** (after 003) | `supabase/migrations/003_open_learning.sql`; `src/pages/Reviews.tsx` | 003 lets anyone insert reviews. The `review_defaults` trigger keeps them `pending` while `reviews.requireApproval` is true (default), so spam is not published, but it fills the moderation queue and the table. If an admin turns approval off, spam and fake names go live immediately. Client-side checks (name, rating, ≥ 20 chars, consent) are trivially bypassed. Confirmed. | Keep `requireApproval` on. Add bot protection (Supabase Auth captcha does not cover PostgREST inserts — use an Edge Function with hCaptcha/Turnstile, or a honeypot field checked in a trigger); add per-IP/day limits in an Edge Function; bulk-delete tooling for pending reviews. |
| 3 | No rate limiting on any anonymous write path | **Medium** | whole data layer (no server) | There is no server to rate-limit; PostgREST inserts are limited only by Supabase platform limits (**Unknown** exact values; check Supabase docs/dashboard). Supabase Auth has its own rate limits (built-in email ≈ 2/hour, confirmed at hand-off). | As #1/#2: Edge Function front door for anonymous writes, or database-level throttling (e.g. reject >N inserts per minute via a trigger counting recent rows). |
| 4 | Migrations 002/003 not applied → policy drift between repo and production | **Medium** | `supabase/migrations/002_user_management.sql`, `003_open_learning.sql`; `docs/DATABASE.md` §1 | Verified at hand-off: production lacks `profiles.blocked` and the 003 review policy. Security-relevant effects: no suspension capability, no admin policies on `admins`/`profiles`, and the repo's `schema.sql` no longer describes the live database, so reviewers may assume protections that do not exist. There is no record of which migrations have run. Confirmed. | Run 002 then 003 in the SQL editor (idempotent). Track applied migrations (a `schema_migrations` table or adopt Supabase CLI migrations) and add a post-deploy check. |
| 5 | Supabase Auth sign-ups may still be enabled | **Medium** | Supabase dashboard (not in repo); `src/data/supabaseStore.ts` lines 80–90; `src/pages/Account.tsx` (`tab` hard-coded to `'signin'`) | The learner sign-up UI is gone, but `POST /auth/v1/signup` with the public key still works unless sign-ups are disabled in Supabase (**Unknown**). Each sign-up creates an `auth.users` row, a `profiles` row and a `signup` event (trigger), sends a confirmation email (consuming the ≈ 2/hour built-in email quota, which could delay the admin's own password-reset emails), and gives the caller the `authenticated` role (can insert `submissions` and reviews with their `user_id`, update their own profile). They cannot become admin. | Supabase → Authentication → Sign In / Providers → disable "Allow new users to sign up" (admins can still be invited/created from the dashboard). Optionally remove `signUp` from `DataStore`. |
| 6 | Password policy only enforced client-side | **Low** | `src/pages/Account.tsx` lines ~203, ~293 (min 8); Supabase Auth settings | The UI requires ≥ 8 characters; the server-side minimum/complexity and leaked-password protection are Supabase settings (**Unknown**). Only the admin has a password in practice. | In Supabase → Auth → Providers/Password: set minimum length ≥ 8 (ideally 12), require character classes, enable leaked-password protection if the plan allows; consider MFA for the admin account. |
| 7 | Admin session stored in `localStorage`; no Content Security Policy | **Medium** | `src/data/supabaseStore.ts` line 33 (`persistSession: true`, supabase-js default storage); `index.html` (no CSP); GitHub Pages (cannot set response headers) | Access and refresh tokens live in `localStorage` (Inferred-from-supabase-js-conventions: key `sb-<ref>-auth-token`). Any XSS on the `github.io` origin could read them and act as the admin until the refresh token is revoked. No XSS sink was found (see #10–#12), which keeps this Medium rather than High. | Add a `<meta http-equiv="Content-Security-Policy">` in `index.html` allowing only `self`, the Supabase project URL (`connect-src`, `img-src`), `fonts.googleapis.com`/`fonts.gstatic.com`, and `frame-src` YouTube-nocookie/Vimeo/`view.officeapps.live.com`/Supabase Storage. Keep sessions short (JWT expiry) and sign out on shared machines. Note: a CSP `<meta>` must be tested with the inline colour-mode script (hash it). |
| 8 | Implicit auth flow puts tokens in the URL fragment | **Low** | `src/data/supabaseStore.ts` line 33 (`flowType: 'implicit'`, `detectSessionInUrl: true`) | Email links (password reset, confirmation) return `#access_token=…&refresh_token=…`. Fragments are not sent to servers or in `Referer`, and supabase-js consumes them on load (Inferred-from-supabase-js-conventions). Residual risk: tokens can remain in browser history or be copied from the address bar if the app fails to load. Chosen deliberately so links work on another device. | Acceptable. Alternative: PKCE flow (`flowType: 'pkce'`) with the trade-off that links must be opened in the same browser. |
| 9 | Media bucket is public-read and listable | **Low** | `supabase/schema.sql` lines 135–141; `src/data/supabaseStore.ts` lines 253–263 | `public = true` means every uploaded object is downloadable by URL; the `media: public read` SELECT policy on `storage.objects` additionally lets anyone **list** the bucket via the Storage API, so files uploaded for unpublished drafts are discoverable. Required by design for images and for the Office viewer. Confirmed. | Tell admins: never upload private documents. Optionally drop the broad SELECT policy (public URLs keep working for a public bucket; admin listing then needs an `is_admin()` SELECT policy) — test before changing. |
| 10 | Upload validation is client-side only; MIME type and extension trusted | **Low** | `src/admin/uploads.tsx` (50 MB, `DOC_ACCEPT`), `src/admin/pages/Media.tsx` (`accept="image/*,…"`, 50 MB check `MAX_BYTES * 10`), `src/data/supabaseStore.ts` `uploadMedia` (`contentType: file.type`) | Size and type checks run in the browser; the file's own `type` is sent as the stored `Content-Type`. The bucket has no `file_size_limit` / `allowed_mime_types` in SQL, so Supabase project defaults apply (**Unknown** values). Only admins can upload (RLS), so this is a defence-in-depth issue. File names are sanitised to `[a-z0-9._-]` and prefixed with a timestamp. Confirmed. | Set bucket limits in Supabase (Storage → bucket settings or `update storage.buckets set file_size_limit = …, allowed_mime_types = '{image/png,image/jpeg,image/webp,image/gif,application/pdf,…}'`). |
| 11 | SVG uploads | **Low** | `src/admin/pages/Media.tsx` (`accept="image/*"` includes SVG; `optimise()` leaves SVG untouched) | SVGs can contain script. Rendered via `<img>` (all app usages) scripts do not run. Opening the file URL directly would run script on the **Supabase Storage origin** (`*.supabase.co`), not the site origin, so it cannot read the admin session in the `github.io` `localStorage`. Whether Supabase Storage adds a restrictive CSP/`Content-Disposition` for SVG is **Unknown**. Only admins can upload. | Exclude `image/svg+xml` via bucket `allowed_mime_types`, or sanitise SVGs before upload. |
| 12 | Markdown renderer | **Info (good)** | `src/lib/markdown.tsx` | Builds React elements only (no `dangerouslySetInnerHTML`; none anywhere in `src/` — Confirmed by search). Link targets pass `safeHref`, allowing only `http:`, `https:`, `mailto:` and paths starting with `/` (everything else becomes `#`). External links get `target="_blank" rel="noreferrer"`. Note: `/` also matches protocol-relative `//host` URLs (open redirect-style link to another site, not script execution). | Optionally reject `//` prefixes in `safeHref`. |
| 13 | Admin-authored URLs rendered without an allow-list (`link`, `video` fallback, `image`, `file` blocks; footer, promo, resource links; PDF `<iframe src>`) | **Low** | `src/components/Blocks.tsx` lines 29, 46–59, 252–279; `src/components/AppShell.tsx`, `src/components/Promo.tsx`, `src/pages/Resources.tsx` | These `href`/`src` values come straight from content JSON. Only admins can publish content (RLS + `publish_content`). React 19.3 (installed) replaces `javascript:` URLs in `href` and `src` with a throwing stub (Confirmed in `node_modules/react-dom`), so script injection via these fields is blocked; `data:` URLs are not blocked but load in an opaque origin in iframes. A PDF block embeds any admin-provided URL in an `<iframe>` without `sandbox`. | Validate URLs in the admin editor (`https:` only, plus Supabase Storage for files); add `sandbox="allow-scripts allow-same-origin allow-popups"` or `referrerpolicy` on third-party iframes where compatible. |
| 14 | Third-party iframes (YouTube-nocookie, Vimeo, Office Online) | **Low** | `src/components/Blocks.tsx` lines 52, 262, 284–290 | Embeds are built from regex-extracted IDs (YouTube/Vimeo) or `encodeURIComponent` (Office), so the iframe host is fixed. Third parties receive viewer IP/UA; Office fetches the file publicly. | Covered by CSP `frame-src` (#7). Mention in a privacy notice. |
| 15 | Browser-stored learner data | **Info** | `src/state/learner.tsx` (`dk.learner.guest`), `src/data/localStore.ts` | Progress, notes, challenge links and optional name are stored unencrypted in `localStorage`. Not sensitive; readable by anyone using the same browser profile or by XSS. | None needed; mention in a privacy notice. |
| 16 | Browser-only fallback if build variables are missing | **Low** | `src/data/index.ts` line 9; `src/data/localStore.ts` lines 94–98 | If `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` are absent at build time, production silently runs in local mode where **anyone** can click "Open admin for this browser". Changes affect only that visitor's own browser, so there is no data exposure, but the live site would stop showing real content. | Fail the CI build when the variables are missing (e.g. a check in `scripts/postbuild.mjs` or the workflow). |
| 17 | Publishable key in the JS bundle (and in git history of `docs/OPERATIONS.md`; redacted from the docs in v2.0) | **Info** (expected) | build output; git history | The publishable/anon key is designed to be public; security relies on RLS. It was written in `docs/OPERATIONS.md` before v2.0 and remains in git history. No secret/`service_role` key, JWT secret or database password was found in the working tree or git history (searched `git log --all -p` for `service_role`, `sb_secret_`, JWT prefixes — only documentation warnings matched). | None required. If the key is ever rotated, update the GitHub variable and `.env.local`, and remove the literal from docs. |
| 18 | Secrets in repository | **Info (good)** | `.gitignore` (`*.local`), `.env.example` | `git log --all --name-only` shows only `.env.example` (placeholder values) ever committed; `.env.local` is ignored. | Keep it that way; consider a secret-scanning pre-commit hook / GitHub secret scanning. |
| 19 | GitHub Actions configuration | **Low** | `.github/workflows/deploy.yml` | Least-privilege permissions (`contents: read`, `pages: write`, `id-token: write`); only official `actions/*` actions; no secrets used; `npm ci` with lockfile. Actions are pinned to major tags (`@v4`, `@v5`, `@v3`), not commit SHAs. | Optional: pin actions to SHAs and enable Dependabot for Actions and npm. Enable branch protection on `main` (every push deploys). |
| 20 | Dependency vulnerabilities | **Low** | `package.json`, `package-lock.json` | `npm audit --omit=dev`: **0 vulnerabilities** in production dependencies (20 prod deps). Full `npm audit`: **2 low** — `esbuild` 0.27.3–0.28.0 (GHSA-g7r4-m6w7-qqqr, arbitrary file read from the dev server on **Windows**, CVSS 2.5) pulled in by dev-only `motion-studio`; npm's suggested fix is a semver-major *downgrade* to `motion-studio@1.5.1`. Not shipped to production. | Accept for now (dev-only, Windows-only); update `motion-studio` when a release depends on `esbuild >= 0.28.1`. Re-run `npm audit` before each release. |
| 21 | CORS | **Info** | Supabase platform | CORS for `/rest/v1`, `/auth/v1`, `/storage/v1` is managed by Supabase (Inferred: permissive for browser clients using the API key). Not configurable in this repo. Access control does not rely on CORS. | None. |
| 22 | Admin can delete the published content row | **Low** | `supabase/schema.sql` lines 60–62 | Policy `content: admin writes draft` is `for all` with USING `is_admin()`; its WITH CHECK (`id = 'draft'`) does not apply to DELETE, so an admin API call could delete `published`. The app never does; visitors would then see the bundled seed. | Split into separate INSERT/UPDATE/DELETE policies each restricted to `id = 'draft'`. |
| 23 | Users can edit their own profile freely (except `blocked` after 002) | **Low** | `supabase/schema.sql` lines 33–35, 207–226 | `profiles: update own` has no column restriction; a signed-in user can change their own `email`, `created_at`, `last_active_at`, `state`, which admins see in Users. Only relevant if sign-ups are enabled (#5). | Extend `protect_profile()` to pin `email` and `created_at` for non-admins. |
| 24 | `content_history` grows without bound | **Low** (availability) | `supabase/schema.sql` lines 64–92 | Every publish stores a full copy of the site JSON; there is no delete policy or pruning. Could approach the free-plan 500 MB limit over time. | Periodic prune in the SQL editor or a `pg_cron` job keeping the latest N versions. |
| 25 | Raw backend error messages shown to users | **Info** | `src/data/supabaseStore.ts` `fail()` | Postgres/RLS/Auth messages (e.g. "new row violates row-level security policy for table …") are shown in toasts. Reveals table names only (already public via the API). | Map common errors to friendly text. |

## 2. What's good

| Practice | Evidence |
|---|---|
| RLS enabled on **every** application table | `alter table … enable row level security` for `admins`, `profiles`, `site_content`, `content_history`, `events`, `submissions`, `reviews` (`supabase/schema.sql`) |
| Admin role in a separate table | `public.admins` with no self-service write path; users cannot make themselves admin by editing their profile (`schema.sql` lines 5–16) |
| Publishing is server-checked and atomic | `publish_content()` raises "Only admins can publish" unless `is_admin()`; published row is not writable directly (WITH CHECK `id = 'draft'`) |
| Review status cannot be chosen by the client | `review_defaults()` BEFORE INSERT trigger forces `status`, `featured = false`, `reply = null` |
| Suspension flag protected (002) | `protect_profile()` BEFORE UPDATE trigger resets `blocked` for non-admins; admins cannot remove themselves from `admins` |
| `security definer` functions pin `search_path` | Every function uses `set search_path = public` (prevents search-path hijacking) |
| Length and value checks in the database | Check constraints on events, submissions, reviews, profiles.level, site_content.id |
| No HTML injection sinks | No `dangerouslySetInnerHTML`/`innerHTML`/`eval` in `src/`; markdown renders React elements with a URL allow-list; React 19 blocks `javascript:` URLs |
| External links hardened | `target="_blank"` links use `rel="noreferrer"` |
| No secrets in the repo or CI | Only the publishable key is used; `.env.local` ignored; workflow uses variables, least-privilege permissions |
| Dev tooling cannot ship | `scripts/postbuild.mjs` fails the build if Motion Studio code reaches `dist` |
| Learners hold no accounts | Progress stays in the learner's browser; no learner PII stored server-side (owner decision) |
| Production dependencies clean | `npm audit --omit=dev` → 0 vulnerabilities |

---

## 3. Recommended order of work

1. Run migrations 002 and 003 on production (fixes drift, enables suspension/admin management and anonymous reviews).
2. Disable public sign-ups in Supabase Auth; review password policy and enable MFA for the admin.
3. Tighten the `events` insert policy (types + server-set `user_name`) and add bot protection / rate limiting for reviews.
4. Add a Content Security Policy `<meta>` tag.
5. Set bucket `file_size_limit` and `allowed_mime_types` (exclude SVG).
6. Split the `site_content` policy, extend `protect_profile`, add history pruning.
